1 · Answering your question first

What happened to the actor

The paper trail

  • 1 ADR 002: XState actors - superseded. todoListsMachine owned selection and spawned one child actor per list. Its exact words: "React stays a thin boundary… TodoListForm still emits intent events through a single send prop." That is the convention you are remembering, verbatim.
  • 2 ADR 003: Shared datom actor - superseded. Kept the actor, moved it into shared/. This is the "separated the shared actor into other parts" step you half-remember.
  • 3 ADR 004: Single datom log - accepted, supersedes 003. shared/src/todoListActor.js (463 lines) and backend/src/todos/createServerTodoActor.js were deleted outright - see docs/plans/single-datom-log.md:101-112. The README now states plainly: "XState is no longer a dependency."

The gap

ADR 004 is exhaustive about the model: the datom, entity ids, attributes, eight numbered rules, the wire protocol, the journal. Search it for how a component reaches that model and you find one sentence - "In-flight text stays in React state" (line 185). The actor convention was removed and no successor convention was ever recorded. DECISIONS.md has sections for persistence, API, ids, lifecycle, edit granularity, ghost composer and StatusBar - none for UI→model.

Three conventions, one function, today

All three of these are live in TodoLists.jsx right now.

1. EVENTS TO A REDUCER

dispatch({ type: 'SELECT_LIST', listId })

The ADR-002 shape. Survived for navigation only, in todoListsUiState.js. It is the one part that reads cleanly.

2. EVENTS TO A SWITCH

send({ type: TODO_UI_EVENT.COMPOSER_CHANGE, text })

The actor's send prop, outliving its actor. sendToList (TodoLists.jsx:218-262) is a switch statement standing where a machine used to be - but it holds no state and has no transitions.

3. NO CONVENTION

client.assert(activeList.id, ATTRIBUTE.TITLE, title)

Raw datom writes inline in JSX props (TodoLists.jsx:355-362). Whatever was quickest once the actor was gone.

This is the actual answer to "why is this too complex." Not bad code - three vocabularies for the same job, none of them wrong on its own.

Why the actor died, and why that reasoning still binds

ADR 004's central observation: "Every user action changes exactly one attribute of exactly one entity, so no user action needs more than one datom to be atomic." Rule 2 then removes conflicts, rejections and rebase entirely - "Last write wins. There are no conflicts, no rejections, and no rebase."

A datom write therefore has no intermediate states. It cannot be pending, cannot fail, cannot conflict, cannot roll back. There is nothing for a state machine to run over - which is precisely why the actor became 463 lines of ceremony around a one-line function call, and why it was deleted. But navigation still has real states - browsing, drafting, confirmingDelete - which is why todoListsUiReducer survived the cull and is still the cleanest thing in the file. The split was correct. It just never got written down as a rule.

2 · The decision that comes before any refactor

Which convention do we adopt, app-wide?

This is your real question, and it outranks everything below - the file layout follows from it. It also deserves an ADR, because it is exactly the kind of thing whose absence caused this. Sections 3 to 6 unpack the recommended one in full.

1Commands only

Every UI→model interaction is a named function call. No events anywhere. Navigation state becomes useState.

commands.renameList(id, title)
commands.completeTodo(todo)

  • +One vocabulary. Shortest path from click to datom.
  • -Throws away the one thing that currently works. drafting and confirmingDelete are genuinely stateful; scattering them into booleans re-creates the illegal states the reducer prevents.

2Events only

Restore the actor spirit without XState. UI only ever calls send(event); a reducer returns [state, effects]; a runner writes the datoms.

send({ type: 'RENAME_LIST', ... })

  • +True continuity with the convention you remember. One door in, everything assertable as data.
  • -Rebuilds by hand what ADR 004 concluded was unnecessary. Most events would carry no state transition at all - just "write this datom" wrapped in an envelope, which is the ceremony that got deleted.

3Demarcated hybrid

Recommended

Keep both, and write down the rule that decides which: events where there are states, commands where there are none.

dispatch(…) → navigation
commands.…() → datoms

  • +It is what the codebase already converged on by instinct - this makes it deliberate and reviewable.
  • +Follows straight from ADR 004: no conflicts and no rollback means a write has no states, so it needs no machine.
  • +Kills convention #3 (raw client.assert in JSX) and #2 (the stateless sendToList switch), leaving exactly two.
  • -Two vocabularies, so the rule must be stated crisply or it erodes again. That is the ADR's job.

3 · The rule, from first principles

Ask one question: what changed?

My first phrasing was "events where there are states, commands where there are none". That is too loose - everything has state, including the composer. Here is the version that actually holds up, and it turns on ownership, not on the presence of state.

The rule

After an interaction, ask what changed, and who owns it.

A FACT ABOUT THE DOMAIN

A title, a text, a completion, a due date, whether something exists.

→ command. The datom log owns it.

WHAT THE SCREEN IS OFFERING

Which list is open, whether we are drafting, whether a dialog is up.

→ event. The screen owns it, and only for this session.

NOTHING - YET

Characters typed into a field that has not settled.

→ neither. In-flight text is a third thing, and it is the bridge.

Both are fixed by putting the person at the top - because events and commands are both things a component does, they just arrive at different owners.

Where events went in the old picture

They were a self-loop on the screen-state box, which drew as an arrow pointing at nothing - so the picture showed the command path and hid the event path. Your read was correct. Events are not a layer; they are how you reach one of the layers, exactly as commands are how you reach another.

The dotted edge you asked about

How: screen state names the active list. TodoListForm is mounted with key={activeList.id} (TodoLists.jsx:349), and React destroys and rebuilds a subtree when its key changes. So a navigation event can unmount a field that still has unsettled text in it. Why it matters: that is the entire subject of section 12.

Why this is elegant, and not merely tidy: the middle layer is the only place in the entire app where timing lives. Above it nothing is debounced; below it nothing is debounced. That is why useSettledText can be 62 lines and still cover every text field in the product - and why a second timer appearing anywhere else is a bug in the architecture, not just in the file.

Why "in-flight text" needs its own layer

It is tempting to call typing a command and be done. ADR 004 explains why that fails:

"Without this, typing a twenty-character Todo would mint twenty datoms on text, nineteen of them superseded within a second, and there is no transaction envelope left to group them."

ADR 004, Edit granularity

The actor used to absorb this - debouncing was one of the things todoListMachine did. When the actor was deleted, that job did not disappear; it moved into useSettledText for two fields, and was re-implemented from scratch for the composer. Naming this layer is what stops that happening a third time.

The tell: if you ever find a setTimeout outside this layer, the convention has been broken. There is exactly one in the app today that should not be there - settleTimers in TodoLists.jsx:119.

One interaction, walked through the picture

The hardest case in the product, traced edge by edge. If this reads clearly, the concept is doing its job.

YOU TYPE "BUY MILK" IN THE COMPOSER, THEN CLICK ANOTHER TODO LIST

  1. thin arrow Keystrokes reach in-flight text. Nothing is a fact yet, nothing is written, no event fires. The screen has not changed what it is offering.
  2. EVENT The click sends SELECT_LIST to screen state. What changed is which list is on screen - a fact about the session, not about the domain.
  3. dotted Screen state names a different active list, so TodoListForm's key changes and React unmounts the composer. This is the edge you asked about, doing real work.
  4. COMMAND Unmount is one of settling's four exits, so the in-flight text settles on the way out and emits addTodo("Buy milk"). A fact now exists.
  5. dotted The datom projects back down, and every mounted field shows the new truth.

Five steps, three owners, two vocabularies, and no step where it is unclear which one applies. Today this same interaction is spread across a Record, a Map, two ref mirrors and five functions in one component - which is the same behaviour, just with nowhere to point at while explaining it.

5 · The state machines

All the state there is

Three machines, and that is the complete inventory - if the convention holds, no fourth one can appear, because facts have no states and rendering has no memory. Every transition below is read off code that exists today; nothing here is aspirational.

screen state Navigation

Read from todoListsUiState.js as it is written today. This is the machine that survived the actor, and it is the one you should judge the others against.

stateDiagram-v2 direction TB [*] --> browsing: SET_ACTIVE, first lists arrive browsing --> drafting: ADD_LIST browsing --> browsing: SELECT_LIST drafting --> browsing: MATERIALIZE, title settled drafting --> browsing: ESCAPE_DRAFT drafting --> drafting: ADD_LIST ignored, focuses the field browsing --> confirmingDelete: REQUEST_DELETE confirmingDelete --> browsing: CANCEL_DELETE confirmingDelete --> browsing: CONFIRM_DELETE, selection moves on

Two edges the code allows but the diagram omits, because no UI reaches them: REQUEST_DELETE from drafting, and ADD_LIST from confirmingDelete. The reducer guards neither. Harmless today because the dialog is modal and a draft has no delete button - but it is exactly the kind of latent hole a state diagram is for. Worth a guard, or worth a comment saying why not.

in-flight text Settling

Read from useSettledText.js. Every text field in the product runs this machine - and under the convention, so would the composer.

stateDiagram-v2 direction TB [*] --> Settled Settled --> Pending: change, starts the timer Pending --> Pending: change, restarts the timer Pending --> Settled: 500ms idle Pending --> Settled: blur Pending --> Settled: Enter Pending --> Settled: unmount Pending --> Settled: reset on Escape, emits nothing Settled --> Settled: new value from the model note right of Pending Every exit except reset emits exactly one command end note

The one subtle rule, worth knowing by heart: in Pending, an incoming value from the model is ignored - "an edit in flight outranks an incoming one; last write wins either way" (useSettledText.js:25). That is the only place the app resolves a race, and it resolves it in favour of the person typing. Every transition out of Pending except reset emits one command.

in-flight text The ghost composer, layered on top of settling

This is the hardest thing in the product and the reason the file grew. It is not a fourth machine - it is the settling machine plus a rule about what each settle means. Read from TodoLists.jsx:164-197 as written today; the states are implicit there, which is precisely the problem.

stateDiagram-v2 direction LR [*] --> Empty Empty --> Typing: change Typing --> Empty: settles blank, nothing written Typing --> Linked: settles non-blank, addTodo() Linked --> Linked: settles non-blank, retitleTodo() Linked --> Empty: settles blank, deleteTodo() Linked --> Empty: Enter or Add, commits the row Linked --> Typing: linked Todo deleted elsewhere note right of Linked While Linked the Todo is hidden from the list, because the field is already showing it end note

Why it earns its complexity

A Todo's defining attribute is text (ADR 004). So "a Todo with no text" is not a valid state in the model - it is unrepresentable. The composer therefore cannot create the Todo when you start typing; it has to wait until there is something to assert. The three states above are the minimum needed to express that, and each maps to exactly one command.

What naming it buys

Today these states exist only as the combination of text, linkedId and a Map lookup, spread across five functions. As useGhostComposer they become three named states in one file with one timer, testable in TodoListForm.stories.jsx where the behaviour actually lives.

Sanity check on the whole concept: notice what is not here. There is no machine for saving, none for conflicts, none for retries, none for offline. ADR 004 removed all four by construction, and StatusBar reports connection health as a pure projection of client status rather than as a state machine of its own. If a future change wants to add one of those machines back, that is the signal that ADR 004's premise has changed - and it should be an ADR, not a hook.

6 · Keeping it from falling through the cracks again

Three defences, in increasing order of strength

This is the part you asked for directly, and it matters more than the refactor. The convention was lost once because it lived only in a superseded ADR and in people's heads. Prose alone will lose it again.

Weakest

1. Write ADR 007

One page: the rule, the three owners, the classification table, and the state diagrams above. Crucially, it should say "this is the successor ADR 004 did not write" and link back to 002 and 003, so the next reader finds the whole chain.

Fails when: nobody reads it. Which is what happened last time.

Better

2. Point AGENTS.md at it

The working agreement already has a "Where things are" table that agents and people actually consult. One row - "How the UI talks to the model → ADR 007" - puts the rule in the path of anyone about to write a component.

Fails when: someone is in a hurry. Better odds, still human.

Strongest

3. Make it a lint gate

An ESLint no-restricted-imports rule: nothing under components/ may import @web-interview/todos/datom, and nothing outside todoListCommands.js may name client.assert or client.retract. Breaking the convention then fails npm run verify.

Cannot fail quietly. It is checked on every run, by machine.

Defence 3 is your own principle, applied to yourself. AGENTS.md already argues it about the verify gate: "Never reason 'this change could not possibly affect Lighthouse' - a path rule cannot be talked into being wrong, and reasoning can." A convention that only lives in prose is reasoning. A convention with a lint rule behind it is a path rule. That sentence is the answer to "how do we stop this falling through the cracks."

8 · Layer membership tests

How to tell which layer a line belongs to

Each layer gets a one-sentence membership test. If a line fails the test, it is in the wrong file. Names are chosen so the file name alone answers "what is in here".

Rendering

Pixels only

Takes plain values, returns JSX, calls callbacks by name.

Test: it never mentions client, readModel, ATTRIBUTE or setTimeout. Same props, same pixels, every time.

Model read

Projection

Turns readModel + navigation state into exactly what the screen needs.

Test: a pure function. No hooks, no refs, no writes. Callable from a unit test with a literal object.

Model write

Domain verbs

The only place client.assert / client.retract and ATTRIBUTE appear.

Test: every export reads like something a user did - renameList, completeTodo - not like a datom.

Timing

When, not what

Decides when a keystroke becomes a write. Owns every setTimeout.

Test: deleting it would make writes happen on every keystroke instead of once - it changes the schedule, never the content.

Focus

The DOM nudges

Refs and effects that move the caret after something changed.

Test: removing it breaks keyboard flow only - no data changes, no rendering changes.

Navigation is the sixth, and it is the one already done well: todoListsUiReducer is a pure state machine with its own tests. Every option below keeps it exactly as it is. Worth naming explicitly so it does not get absorbed back into "the hook".

10 · The piece every option shares

First, give the writes a name

This is not one of the three options - it is a prerequisite all three want, and it is the single highest-value extraction on its own. Right now ATTRIBUTE.TITLE and client.assert appear inside JSX props (TodoLists.jsx:355-362). After this, they appear in exactly one file.

proposed todos/todoListCommands.js Model write

What this earns

  • +ATTRIBUTE stops leaking into components entirely.
  • +The "read before you write" rule (find the todo, check it exists, retract the old dueDate before asserting a new one) lives in one place instead of being restated at each call site.
  • +Unit testable against a fake client - no React, no DOM. Matches the coverage policy in docs/adr/005, which gates non-UI logic near 100%.
  • +The TODO_UI_EVENT switch in sendToList collapses: the events already map one-to-one onto these verbs.

What this settles about TODO_UI_EVENT

Under the rule in section 3 it goes away. All five of its events - COMPOSER_CHANGE, COMPOSER_SUBMIT, COMPOSER_COMMIT, TODO_PATCH, TODO_REMOVE - resolve to a datom write with no state transition, so they are commands wearing an event costume. sendToList's switch (TodoLists.jsx:218-262) is the last visible piece of the deleted actor: a dispatcher with nothing to dispatch to. todoListsUiState.js keeps its events, because it has actual states.

12 · A behaviour question, already answered

What option B changes for the user

Today the composer's unsettled text lives in the parent, so it survives switching lists. If the composer moves into TodoListForm, unmount settles it instead - the same thing useSettledText already does for Todo text and list titles. No typing is lost either way; it lands in a different place.

Checked before asking: DECISIONS.md, under "Edit granularity: mint on settle", already says "Leaving a field by switching Todo Lists settles rather than discards, so the edit survives." That is the documented rule, and the composer is the one field that does not follow it. So option B is not a behaviour change to be argued for - it brings the composer into line with a decision the repo already made.

Today

Type "Buy milk", switch list, switch back

The composer still reads Buy milk. A ghost Todo may have been created behind it by the timer that kept running in the parent's Map - but it is filtered out of the visible rows, so you see no new Todo row.

With option B

Same three actions

Unmount settles immediately, so Buy milk becomes a real Todo row. Switching back shows an empty composer and Buy milk in the list.

Still worth your eyes: the documented rule was written about fields, and the composer is a field with an extra job - it also decides whether a Todo exists at all. Reading the rule as covering it is a judgement, not a quote. No story pins today's behaviour either way, so if you read it differently, option B still works with the draft left lifted; the win just shrinks to deleting the timer Map while keeping the Record.

14 · Recommendation

Write the convention down, then B, then A

  1. Write ADR 007: how the UI talks to the model. One page. It records the rule from section 3, the hierarchy from section 4 and the state diagrams from section 5, and states outright that it is the successor ADR 004 never wrote after retiring the actor. Without this the next refactor re-invents a fourth convention. This is the step your question was actually asking for.
  2. Add the AGENTS.md row and the lint gate (section 6, defences 2 and 3) before the refactor, not after. The gate will fail immediately - that is correct, it is measuring the work still to do, and it goes green exactly when step 4 lands.
  3. Extract todoListCommands.js. The command half of the rule, made real. No behaviour change, gets ATTRIBUTE out of JSX, and collapses sendToList - the actor's last remnant.
  4. Then option B. The step that removes complexity instead of relocating it: the Map, the Record and both ref mirrors stop existing because the composer is mounted once.
  5. Then option A's useTodoListsScreen, over what is left - navigation, projection, focus. By then it is a thin composition, not a god-hook, because the hard part already moved down.
  6. Leave C on the shelf. It is convention #2 in disguise; revisit only if this screen grows genuinely stateful writes, which ADR 004 rule 2 says it will not.

One thing I could not verify: whether dropping the actor convention without a successor was a conscious call at the time or simply fell through the cracks during a large deletion. docs/plans/single-datom-log.md tracks the files removed, not the conventions. You would know better than the repo does - and if it was deliberate, step 1 should record that reasoning instead of mine.

How to keep this honest: the repo's own rule is to reproduce behaviour before touching code. Before any of this, the composer behaviours worth keeping - ghost materialize on settle, dematerialize on blank, the switch-lists case - should be pinned by story plays. GhostComposerLifecycle in TodoLists.stories.jsx:281 covers the first two; the switch-lists case is not covered today, which is exactly why step 6 is a question rather than a fact.
