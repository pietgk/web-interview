Implementation plan

Todo List lifecycle and StatusBar

Add, rename, sort, and delete Todo Lists through the existing optimistic local-first transaction model, while replacing scattered save text with one extensible global StatusBar.

Outcome

The full Todo Lists read model remains the single rendered source. Every valid list mutation becomes an optimistic transaction, is durably queued in IndexedDB, synchronizes after the existing 400 ms debounce, and is confirmed by the backend's complete authoritative read model.

StatusBar, not AppBarAn outlined, sticky global status surface starts with the permanent “Things to do” heading and can later coexist with a bottom DevBar.
One title fieldThe active card's “Todo List name” field handles both initial naming and later renaming. No second name input appears in the collection.
Derived urgencyNext Due Date, completion, counts, and display order are all selectors over the optimistic complete read model.

Current to target

Current

  • Filled blue AppBar carries only the page title.
  • Save state is a small line inside the active Todo List.
  • Switching or deleting a list can hide its pending or failed state.
  • Todo Lists are seeded entities without create, rename, or delete transactions.
  • Navigation uses stored order and completion summary only.

Target

  • Outlined StatusBar is the stable top application region.
  • Status parts explain local durability, backend synchronization, and recovery.
  • One runtime snapshot drives StatusBar and all Todo List UI.
  • Todo List lifecycle uses the same transaction, outbox, sync, and journal path as Todos.
  • Navigation derives urgency order, completion, counts, and Next Due Date.

Runtime and persistence flow

The seam moves up to application composition: useTodoLists() creates one runtime, then its small interface is passed to both the StatusBar and Todo Lists modules. No second actor or storage adapter is created.

StatusBar state model

One pure selector returns severity, ordered status parts, a state-specific primary action, optional Details, and optional dismissal. The first applicable row wins; lower-priority facts may become supporting parts.

MUI 5.18 only renders its automatic onClose icon when no action prop exists. When Review and dismissal coexist, the StatusBar action group renders Details plus an equivalent close IconButton.

Implementation sequence

  1. Specify outcomes in shared tests

    Add failing tests for create, rename, tombstone delete, replay, Next Due Date, display ordering, and global status priority. Preserve current journal replay behavior where list/deleted is absent.

  2. Extend the shared transaction model

    Implement protocol, schema, database, transaction, actor, and selector changes. Confirm the same actor implementation works for IndexedDB and authoritative JSONL adapters.

  3. Lift the runtime seam and add StatusBar

    Create one runtime in App, remove MainAppBar and per-list SaveStatus, then implement status parts, action routing, details, dismissal, accessibility, and scroll layout.

  4. Add Todo List lifecycle UI

    Implement the blank draft, one title field, plus action, list trash actions, confirmation, focus restoration, validation, live sorting, and automatic selection.

  5. Exercise real user journeys

    Run Playwright through optimistic updates, the 400 ms debounce, offline IndexedDB reload, reconnection, backend sync, JSONL durability, delete rollback, and responsive keyboard behavior.

  6. Finish engineering verification

    Fix every test, lint, type, build, accessibility, focus, and visual regression found. Review the final UI at desktop and narrow widths before handoff.

Risks and controls

Legacy journal compatibilityOlder records have no list/deleted. Treat absence as false and add a replay test before changing validation.
Invalid nested button markupA trash IconButton cannot live inside ListItemButton. Use a ListItem secondary action so select and delete remain sibling controls.
Draft auto-selection raceInitial auto-selection must not overwrite an active blank draft. Model draft and existing selection explicitly.
Status flicker and announcement spamCollapse transient actor states into the three agreed autosave stages and announce only changed status parts.
Deletion hidden while offlineThe tombstone transaction is durable in IndexedDB and replayed optimistically after reload before backend synchronization.
Rejected list mutation loses contextRetain enough rejection metadata for a human-readable Details dialog while keeping raw datoms out of the normal UI.
