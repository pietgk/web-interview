Three namings for the same picture

Same scenario every time: one Owner, Alice, with a server, a browser, a phone, and an agent; a second Owner reachable only by a message. Only the words change. Colors are the same across all three: blue is data that is fact, purple is data that is derived, green is a thing that acts, orange is the party that is accountable.

Fixed in every alternative, because the earlier questions settled them:
  • Datom is the Event. A Datom is one fact asserted or retracted, and it is the only event type there is. Commands produce Datoms. This was missing from the first drawing and the spec will state it in the first paragraph.
  • Log is the event store: append-only, one Datom per record, has an epoch.
  • Read Model is derived, hosted by a Read Model Engine.
  • Owner is the accountable party, not a box in the mechanism.

App
The whole: one Log plus every Actor of it. One Owner, one App. The brief's own word: "the actor that owns the app".
Actor
A process that holds state and acts: the Journal, each client, each agent. Every Actor except the Journal holds Facts, some Read Models, and can run Commands.
Journal
The Actor that holds the Log. What the repo calls the server.
Facts
An Actor's local copy of the current set plus its cursor. Data, not a doer. The old "Replica", renamed to say what it is.
Message
What Actors exchange. Inside an App the sync protocol is Messages carrying Datoms. Between Apps a Message is input that the receiving Owner's Command may turn into Datoms.
  • Data and doers separated: Facts / Log / Read Model are data, Actor is the doer.
  • Server, client, agent are visible again as kinds of Actor.
  • "Message" unifies sync and cross-App communication.
  • Owner, App, Actor read as three distinct levels: who, what, which process.
  • "Actor" carries actor-model expectations (mailbox, supervision) we do not promise.
  • Journal is an Actor with no Facts of its own, an exception to the pattern.

System
The whole. Generic, collides with everything.
Event Store
The Log. Event is the Datom.
Server / Client
The doers, by role. An agent is a Client.
Command Handler
Where Commands become Events.
Projection
A Read Model, by its textbook name. Engine is implied.
  • Zero invented words. Any CQRS-ES reader is at home in one minute.
  • Event is front and center.
  • The local copy of current facts has no name at all; textbook CQRS does not have one because clients normally do not hold the whole set. That is our most distinctive property and this vocabulary hides it.
  • "Client" and "Server" describe topology, not what a thing holds or may do. An agent that runs in the server process is neither.
  • "System" is the weakest possible name for the thing an Owner owns.

Space
The whole. One Owner, one Space.
Node
A process in the Space. The origin Node holds the Log; every other Node holds Facts and Read Models.
Facts
As in Alternative 1.
  • Node is neutral: says "a place in the topology" and nothing about behavior, so it never over-promises.
  • Origin Node fits the pattern better than "Journal Actor" does.
  • Node says nothing about acting. Commands have no home; they are drawn as arrows because there is no doer to put them in.
  • "Space" is pleasant but arbitrary. It will need a definition every time.
  • Feels like a network diagram, not an architecture with intent in it.

Recommendation and what to check

Alternative 1. It is the only one where every word answers a different question: Owner says who is accountable, App says what they own, Actor says which process is acting, Facts and Log say what is held, Read Model says what is derived, Datom says what an event is. It uses the brief's own word for the whole, "app", and it gives the doers back their place without smuggling topology in. The actor-model baggage is manageable with one sentence in the glossary: an Actor here holds state and acts; mailboxes and supervision are not implied.

If Journal-as-an-Actor-without-Facts bothers you, the fix inside Alternative 1 is to say the Journal's Facts are the Log, which is literally how the server works today: it folds the journal into a store on startup.

Q1. Does "App" work for you as the name of the whole, given the brief already uses it? Or does it feel too product-shaped for something an agent owns?
Q2. Is "Actor" the right word for the doers, with the one-sentence disclaimer, or do you want a word with no actor-model history?
Q3. "Facts" for the local current set: clear, or too close to "the facts in the Log"?
Q4. Sync as Messages between Actors of one App: does unifying sync and cross-App communication under one word help, or should intra-App sync stay a protocol and Message stay reserved for crossing between Apps?
